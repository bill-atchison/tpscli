tpscli — IT Support User Guide

One command-line executable that runs DESCRIBE, SELECT, INSERT, UPDATE and DELETE against any TopSpeed .TPS file, reading the table layout from the file itself.

Applies to: tpscli 0.1.0 · Windows, any Clarion TopSpeed data file · build 6b35bc9

At a glance

Purpose

Look inside a TopSpeed data file, pull rows out of it, and correct rows in place from a shell or a script, without a Clarion dictionary, an ODBC driver or a rebuild when the file's layout changes.

Audience

IT and field support staff who inspect or repair .TPS files on a register, back office or file server, and anyone scripting against those files.

Prerequisites

A Windows machine, tpscli.exe copied onto it, read (or read/write) access to the .TPS file, and the owner string when the file is encrypted.

Overview

tpscli takes one SQL statement, opens the .TPS file the statement names, does what the statement says, and prints one JSON object (or, with --table, a text grid) before exiting. Writes go through the real TopSpeed driver, so every key in the file is maintained exactly as the owning application maintains it. Each run is one process and one statement; there is no server, session or configuration file.

ScopeRow-level work only. tpscli cannot create, alter, drop, pack or rebuild a file, join two files, aggregate, or run more than one statement per invocation. For any of those, use the owning application or the Clarion tools.

What you type

tpscli.exe [--owner <string>] [--table] [--limit-default N] [--parse-only] "<sql>"
tpscli.exe [options] < statement.sql
tpscli.exe --version

The statement is the first argument that does not start with --. Wrap it in double quotes so the shell passes it whole. If no statement argument is given, tpscli reads the statement from standard input, which is how a script feeds it a file. The table name inside the SQL is the path to the .TPS file, written in square brackets: [C:\pos\data\ITEMS.TPS]. Brackets are required when the path has a drive letter, backslashes or spaces.

The five statements

DESCRIBE [file]
SELECT <cols | *> FROM [file] [WHERE <expr>] [ORDER BY <col> [ASC|DESC], ...] [LIMIT n [OFFSET m]]
INSERT INTO [file] (<cols>) VALUES (<values>)
UPDATE [file] SET <col> = <value>, ... WHERE <expr>
DELETE FROM [file] WHERE <expr>

WHERE accepts =, <>, !=, <, >, <=, >=, AND, OR, NOT, parentheses, LIKE (with % and _), IN (...) and NOT IN (...). Text literals go in single quotes; a quote inside a literal is doubled. Dates are written '2026-09-15' and times '13:45:00'. Group members use a dot (ADDR.CITY) and array elements a 1-based subscript (QTY[3]). UPDATE and DELETE without a WHERE are refused.

Options

tpscli has no configuration file, registry keys or environment variables. Everything is set per invocation on the command line.

OptionValueWhereNotes
--owner <string>The file's owner (encryption) stringCommand line, before the SQLRequired for an encrypted file. Never echoed in output or error messages. Wrong or missing string gives OWNER_WRONG / OWNER_REQUIRED, exit 2.
--tableflagCommand linePrints an aligned text grid instead of JSON. Exit codes and behaviour are otherwise identical; the last line is (n rows) or CODE: message.
--limit-default N0 to 2147483647Command lineCaps a SELECT that has no LIMIT. Default 1000. 0 means no cap.
--parse-onlyflagCommand lineChecks the statement's syntax and column names against the file, then stops. Opens the file to read the layout; never touches a record. Use it before every write.
--versionflagCommand linePrints { "ok": true, "op": null, "version": "0.1.0", "complete": true } and exits 0. The quickest way to confirm the copy on a machine runs.

Four further options (--dump-def, --dump-schema, --walk-key, --selftest) exist for the test suite and are not part of the supported surface.

CautionThe owner string is the one input that, if wrong, stops everything on an encrypted file, and tpscli deliberately never prints it back. Keep it where the site keeps its other secrets, and when a colleague reports OWNER_WRONG, compare the string they used against the source of truth rather than the exe's output.

Procedures

Install tpscli on a machine

  1. Copy tpscli.exe (about 1.7 MB) into a folder on the machine, for example C:\Tools\tpscli\. It is statically linked: no DLLs, no Clarion runtime, no installer and no registry entries are needed.
  2. Open a Command Prompt or PowerShell window in that folder.
  3. Run tpscli.exe --version. You should see { "ok": true, "op": null, "version": "0.1.0", "complete": true }.
  4. Optionally add the folder to the machine's PATH so the exe can be run from any directory. Relative file paths in a statement resolve against the current directory, not the exe's folder.
Tiptpscli opens the data file in shared mode, so it can be run while the owning application has the file open. A row that application is holding at that moment is reported as RECORD_HELD; rerun after the hold clears.

Inspect a file's layout

  1. Run tpscli.exe "DESCRIBE [C:\pos\data\ITEMS.TPS]", substituting the real path.
  2. Read the JSON: records is the row count, columns lists every field with its type (and size, places, dim or nested members where they apply), and keys lists every key with its components and whether it is primary or unique.
  3. If the reply is OWNER_REQUIRED, the file is encrypted: repeat with --owner <string> in front of the statement.

Look at rows

  1. Add --table for a human-readable grid: tpscli.exe --table "SELECT ID, NAME, CODE FROM [C:\pos\data\ITEMS.TPS] ORDER BY ID LIMIT 3".
  2. Narrow with WHERE, for example WHERE NAME LIKE 'b%' or WHERE CODE IN ('A','E'). Column names must match the DESCRIBE output; an unknown name is refused and the message lists the valid ones.
  3. Check the last line. (3 rows, truncated by LIMIT) means more rows matched than were printed; raise LIMIT or use OFFSET to page. Without a LIMIT, a SELECT stops at 1000 rows unless --limit-default says otherwise.
> tpscli.exe --table "SELECT ID, NAME, CODE FROM [testdata\KEYS.TPS] ORDER BY ID LIMIT 3"
ID  NAME     CODE
--  -------  ----
 1  Able     A
 2  baker
 3  Charlie  C
(3 rows, truncated by LIMIT)

Change data safely

  1. Copy the .TPS file somewhere safe first (copy ITEMS.TPS ITEMS.TPS.bak). tpscli has no undo; a multi-row write that fails part-way is rolled back, but a write that succeeds is permanent.
  2. Write the UPDATE, INSERT or DELETE with a WHERE that names the exact rows. Run a SELECT with the same WHERE and confirm the row count is what you expect.
  3. Dry-run it: tpscli.exe --parse-only "UPDATE [C:\pos\data\ITEMS.TPS] SET RECALLED = 0 WHERE SKU = '000379493'". Success looks like { "ok": true, "op": "update", "parse_only": true, "complete": true }. Anything else is a syntax or column problem to fix before going on.
  4. Run the same statement without --parse-only. A successful UPDATE or DELETE replies with matched and affected; a successful INSERT replies with affected: 1.
  5. Confirm with the SELECT from step 2, then check the exit code: echo %ERRORLEVEL% in cmd, $LASTEXITCODE in PowerShell. 0 is the only success.
CriticalDELETE FROM [file] WHERE 1 = 1 deletes every row in the file, and tpscli will do it: the refusal only covers a DELETE or UPDATE with no WHERE at all. Never run that form on a live file without the backup from step 1. Also: if the output ends without the closing "complete": true (the window closed, the process was killed, the machine lost power), the outcome of that write is unknown. Do not assume nothing happened and do not simply rerun it; SELECT the rows first and decide from what is actually there.

Work with an encrypted file

  1. Put --owner <string> before the statement on every call: tpscli.exe --owner <string> "DESCRIBE [C:\pos\data\SECRET.TPS]". The option is per invocation; nothing is remembered between runs.
  2. On a shared machine prefer feeding the statement through a file (tpscli.exe --owner <string> < statement.sql) or a script so the string does not sit in a shell history you cannot clear.
  3. Do not expect the string in any output, log or error text. If you need to prove which string was used, look at your script, not at tpscli.

Call tpscli from a script

  1. Read standard output only. Errors are JSON too, on the same stream, so a script parses one object per run. Standard error carries nothing a script needs.
  2. Check the exit code before trusting the object: 0 ran, 1 was rejected before anything changed, 2 could not open the file, 3 failed while running (see the table below).
  3. Run each call under a timeout. If a Clarion executable crashes it can stop behind a modal dialog instead of exiting, and a script with no timeout waits forever. The project's own test helper, tests\TestHelpers.ps1 (Invoke-Tpscli_Bounded), shows one way to do this from PowerShell.
  4. Treat a response with no "complete": true as unknown, and never retry a write on that basis alone.

Reading the response

Every reply carries ok, op and, as its last member, complete. What sits between them depends on the statement.

StatementSuccess membersExample
DESCRIBEfile, encrypted, records, columns, keys{ "ok": true, "op": "describe", "file": "...", "encrypted": false, "records": 5, "columns": [...], "keys": [...], "complete": true }
SELECTcolumns, rows, row_count, truncated{ "ok": true, "op": "select", "columns": [{"name":"ID","type":"LONG"},{"name":"NAME","type":"STRING"}], "rows": [[2,"baker"]], "row_count": 1, "truncated": false, "complete": true }
INSERTaffected{ "ok": true, "op": "insert", "affected": 1, "complete": true }
UPDATE / DELETEmatched, affected{ "ok": true, "op": "update", "matched": 1, "affected": 1, "complete": true }
any, with --parse-onlyparse_only: true{ "ok": true, "op": "update", "parse_only": true, "complete": true }
failureerror.code, error.message, and for writes outcome{ "ok": false, "op": "delete", "error": { "code": "WHERE_REQUIRED", "message": "DELETE without WHERE is refused. Use WHERE 1 = 1 to delete every row.", "position": 32, "token": "<eof>" }, "outcome": "none", "complete": true }

Values print as: dates YYYY-MM-DD, times HH:MM:SS.hh, decimals as exact strings with trailing fraction zeros trimmed ("10" for 10.00), BLOBs as base64. A string literal longer than its column is stored truncated and the reply adds a warnings array with STRING_TRUNCATED; that is not an error.

ExitMeaningData changed?
0The statement ran; ok is true.Yes for a write, as reported by affected.

2File error: FILE_NOT_FOUND, OWNER_REQUIRED, OWNER_WRONG, DEFINITION_UNREADABLE, DEFINITION_MISMATCH, UNSUPPORTED_FIELD_TYPE.No.

Troubleshooting

SymptomLikely causeFix
"code": "FILE_NOT_FOUND", "message": "File not found: ...", exit 2The path in the brackets is wrong, or it is relative and the current directory is not where you think.Use the full path with a drive letter inside [...]. Check the message: it echoes the path exactly as tpscli tried it.
"code": "OWNER_REQUIRED", "message": "Not a plain TopSpeed file; if it is encrypted pass --owner", exit 2The file is encrypted, or it is not a TopSpeed file at all.Rerun with --owner <string>. If it still fails with OWNER_WRONG, confirm the file really is a .TPS from this application and that the string is the one that application uses.
"code": "OWNER_WRONG", "message": "Owner string does not decrypt this file", exit 2The owner string does not match the file.Check the string against its source of truth. tpscli will not print the one you supplied.
"code": "SYNTAX", "message": "Expected DESCRIBE, SELECT, INSERT, UPDATE, or DELETE", "position": 1, "token": "SELEC", exit 1A typo, a statement outside the five supported, or the shell split the statement because it was not quoted.Fix the token the message names at the given character position. Wrap the whole statement in double quotes.
"code": "SYNTAX", "message": "Unknown option --bogus", exit 1A misspelt option, or an option placed after the statement where it was taken as a second positional argument.Use only the options in the table above, all before the SQL.
"code": "UNKNOWN_COLUMN", "message": "Unknown column NOPE; valid columns: ID, NAME, CODE, AMOUNT", exit 1The column name is not in this file's layout.Pick one from the list in the message, or run DESCRIBE. Group members need the dot form (ADDR.CITY).
"code": "WHERE_REQUIRED", exit 1UPDATE or DELETE with no WHERE.Add a WHERE that names the rows. Only use WHERE 1 = 1 when you truly mean every row and have a backup.
"code": "UNSUPPORTED", exit 1Valid SQL outside the subset: JOIN, GROUP BY, COUNT(*), IS NULL, arithmetic in a WHERE, LIMIT on a write, a fifth ORDER BY column.Rewrite within the five statements. There is no NULL in a TopSpeed file: compare to '' or 0 instead.
"code": "DUPLICATE_KEY", exit 3The insert or update would create a second row with the same value in a unique key; the message names the key.SELECT for the existing row and decide whether to update it instead.
"code": "RECORD_HELD", exit 3, "outcome": "rolled_back"Another process (usually the owning application) holds one of the matching rows. Nothing was changed.Wait for the hold to clear, or run when the application is idle, then rerun. tpscli does not retry on its own.
"code": "VALUE_OUT_OF_RANGE", exit 3A literal cannot be stored in its column: a fraction in an integer, an invalid date such as '2026-02-30', too many digits for a decimal, invalid base64, or text a picture column cannot read.Check the column's type and size in DESCRIBE and correct the literal. The message names the column.
Output ends with no "complete": true, or the exe never returnsThe process was interrupted, or a runtime fault left it behind a modal dialog.Look at the machine for a dialog and close it. Treat the write's outcome as unknown: SELECT the rows before doing anything else. Always run scripted calls under a timeout.
DESCRIBE reports a decimal one digit wider than the dictionary, or a two-dimensional array as one flat dimensionKnown limits of what the file stores: an even-width DECIMAL is indistinguishable from the next odd width, and DIM(a,b) is stored as a single extent.Not a fault. Address the array with one flat subscript (GRID[5] rather than GRID[2][2]). See the README's Deviations section.
A key or index shows zero rows, or ORDER BY on it is ignoredAn INDEX is only populated when the owning application builds it; tpscli never does, and never orders by one.Order by a real key or accept the in-memory sort. Not a data-loss condition.
