Task 1 — Skeleton: static console build, stdout, args, JSON errors · 5720c39

Task 1 · Done · 5720c39

Clarion facts the plan got wrong or did not know

  • Brace escaping: a literal { in a Clarion string is {{; } is never doubled. The plan's JSON literals were right; the first implementation "fixed" them and the review reverted that.
  • MATCH(…, Match:Regular) has no {m,n} quantifier. --limit-default now uses ^[0-9]+$ plus a LEN() > 10 guard. Every later regex in the plan (date {4}, decimal {1,15}, base64 groups) must be written the same way.
  • StringTheory.SetSlice does not grow the string (StringTheory.clw:9042); ReplaceSlice does. JStr's \u00XX escaping was collapsing to one byte until this was switched, and the plan's LOOP i = 1 TO st.Length() froze the bound, so the loop is now LOOP WHILE i <= st.Length().
  • A StringTheory member cannot be embedded by value in a CLASS; StdinBuf is &StringTheory, NEW'd in Init. Not disposed (single process-lifetime instance); deferred minor.
  • Environment: NoDefaultCurrentDirectoryInExePath=1 on this machine, so shell checks call .\tpscli.exe.

Task 2 · Done · 03862e9

Empirical oracle facts Task 4 must reproduce

  • Labels are prefixed (AT:D); DECIMAL(7,2) reports size 7, places 2; CSTRING(21)/PSTRING(21) report size 21; STRING(@N9.2) reports size 9, picture "N9.2"; SHORT,DIM(4) reports size 2, dim 4.

  • Assigning a DIM'd leaf inside a DIM'd group is GR:Phones[i].Ext[j], not a combined subscript.
  • Generator now fails loudly: every CREATE/OPEN/ADD is followed by a stderr message and HALT(1) on ERRORCODE(). A local named line made ADDRESS(line) ambiguous; renamed.

Task 3 — tpsSchema A: header, decrypt, pages, records, merged definition · 50d2f90

Task 3 · Done · 50d2f90

Empirical findings from the corpus

  • LONG wraps two's-complement (--selftest: wrap=-2147483648, wrap2=2147483647, bshift=-2147483648), so the decrypt port uses plain LONG arithmetic, no ULONG masking.
  • Every corpus file is one RLE-compressed page and its definition record is a single block (maxblk 0). Multi-block merging is implemented but not exercised by the corpus.
  • Header counts decoded (fields/memos/indexes): ALLTYPES 15/0/1 (def 307 bytes), KEYS 4/0/5, GROUPS 14/0/1, MEMOS 2/3/1 (driverVersion 2), NOKEY 2/0/0, SECRET 2/0/1 (encrypted, 68 bytes). Decoded labels (AT:ID, SC:ID) match the Task 2 oracle.
  • A file with no tOpS signature and no --owner reports OWNER_REQUIRED (the plan allowed either that or DEFINITION_UNREADABLE).

Task 4 — tpsSchema B: definition parser and DESCRIBE parity · 497a7c8

Task 4 · Done · 497a7c8

TPS definition encoding, pinned against the DynFile oracle

  • DECIMAL size: the definition stores the packed-BCD byte count (D(7,2) → 4, Amount(9,2) → 5); DynFile wants digits, so Size = 2*bytes - 1.
  • Memo flags: bit 0x02 = BINARY (Notes 0x1, Bin 0x3, Pic 0x5), bit 0x04 = BLOB. The plan guessed 0x04 for both.
  • Key flags: 0x10 = PRIMARY confirmed on PKey only. An INDEX (type bits nonzero) has DUP clear in the file but DynFile reports dup 1; tpscli forces Dup=1 for every INDEX (single data point, KEYS.Idx).
  • Key component ordinals are 0-based (fno + 1 correct as planned). CSTRING/PSTRING sizes are stored as declared. OVER resolves by equal offset.
  • DIM(2,3) is stored only as 6 elements; GRID is one-dimensional to tpscli (GRID[1]..GRID[6]), Dim2 = 0.
  • The plan's GROUP member-count loop called a queue-mutating helper inside its comparison and miscounted; the group end offset is now computed before the inner loop. INSTRING argument order in the plan's DESCRIBE path extraction was wrong (it is INSTRING(sub, string, step, start)).
  • --dump-schema prints prefixed labels (AT:D) so the parity test is a literal compare; it also carries a debug flags member on memos and keys.
  • Non-DECIMAL scalar and GROUP sizes come from Bytes / Elements when the entry carries no explicit size.
  • Review fixes: buf/size restored on every Parse return; key component ordinals validated so a bad definition fails closed as DEFINITION_UNREADABLE. Parked: unused SchFieldOffsetEnd/Of, the debug flags member.

Task 6 — tpsSql: tokenizer, parser, columns, expressions, --parse-only · 141e32d

Task 6 · Done · 141e32d

Decisions the plan left open

  • Fixed-width STRING padding is a systemic Clarion trap. Take()/Peek() returned the raw STRING(1024) token; every keyword comparison passed (Clarion = ignores trailing blanks) but every WHERE built by & carried kilobytes of spaces. Fixed at the two funnel points plus every fixed-STRING local that reaches a concatenation. A temporary --dump-where hook found it; --parse-only never would have.
  • Whole-array vs GROUP targets: a GROUP in INSERT/UPDATE is UNSUPPORTED "Assign individual leaves"; a dimmed leaf without a subscript is UNKNOWN_COLUMN (add [n]). The plan said both in different places.

  • JOIN test line changed to JOIN OTHER: a bracket path after JOIN is not a path token by the tokenizer rule, so the backslash fired "Unexpected character" first.
  • Coverage gaps: GROUP BY/HAVING/DISTINCT/UNION/SUM/MIN/MAX/AVG share COUNT's lookup but have no test line; the 40-name UNKNOWN_COLUMN cap and OFFSET-without-LIMIT are untested.
  • Review fixes: duplicate-column errors now report the duplicate's own position (it was read after the token was consumed); bare GROUP is only UNSUPPORTED when followed by BY. Parked: the error-JSON block and op-name CASE are repeated three times in tpscli.clw.

Task 7 — tpsExec: SELECT with JSON rows and --table · 60448d3

Task 7 · Done · 60448d3

WHAT() cannot address a leaf inside a DIM'd GROUP

Deviation (spec/plan). WHAT(rec, fieldIdx, n) only walks the field's own elements; for KIND inside PHONES,DIM(2), element 2 returns NULL, and for EXT it returns PHONES[1].EXT[2], never PHONES[2]. Proven with a probe on GROUPS.TPS. WHAT(rec, groupIdx, 2) does return the 17 raw bytes of PHONES[2], so SELECT slices string leaves out of the group occurrence by offset. EVALUATE has no equivalent: WHERE PHONES[2].KIND = 'M' ran for seconds and exited 0 with no output, so the parser now rejects a WHERE reference with GrpElem > 0 as UNSUPPORTED. Plain array subscripts (WHERE ARR[2] = 20) work. Numeric leaves inside a DIM'd group are UNSUPPORTED in SELECT (nothing in the corpus has one). Task 6's flattening formula is retired for this case; OutColQ keeps GrpElem and Elem separate.

Task 7 · Done · 60448d3

Runtime traps found the hard way

  • A QUEUE,TYPE named PosQ crashes NEW with an access violation (10-line standalone repro); renamed SortQ. This was the source of both crash logs.
  • A crashed exe sits behind the Clarion runtime's modal dialog; two agent runs stalled for hours. Every exe invocation now runs under a timeout, and tests\select.ps1 does too.
  • Calling builtin FORMAT() inside a method named Format resolves to the method; padding is done with SUB/ALL instead.
  • LIKE(ColQ)/LIKE(SchFieldQ) locals do not match by-value queue-row parameters; plain TYPE-name locals do.
  • A ROUTINE reused the caller's loop variable i and repeated a row in the sort fallback.
  • tpsOut.JStr now escapes bytes ≥ 128 as well as < 32 (BIN's CHR(255) produced invalid JSON).
  • --table now prints CODE: message for parser and schema errors too, not only executor errors.
  • Review fixes: all three test scripts run the exe under a 20-second timeout; ORDER BY on a leaf inside a DIM'd group is rejected as UNSUPPORTED (it silently mis-ordered before). Parked: DoSelect+EmitRow length (~190 lines, shared scan state), NOCASE key selection for case-sensitive ORDER BY, table-mode unescape scope.

Task 8 — INSERT · 08b7ce1

Task 8 · Done · 08b7ce1

DECIMAL literal width came from the wrong schema field

Plan-vs-repo mismatch, fixed outside the task's file list. The plan says SchFieldQ.Digits is the decoded digit count. It is not: the TPS definition stores packed-decimal bytes there, and Task 4 decodes the true width into Size (2*bytes-1). Task 6's SqlLitConvert used Digits, so INSERT ... D = 12345.67 into a DECIMAL(7,2) was rejected as "overflows DECIMAL(4,2)" before the executor ever ran. One-line fix in tpsSql.clw, regression case in tests\insert.ps1. Ruling: accepted; Digits is misnamed and is a Task 10 rename candidate.

Task 8 · Done · 08b7ce1

Where VALUE_OUT_OF_RANGE actually fires

The parser (ParseBody → SqlLitConvert) already converts every INSERT literal at parse time, so bad dates, out-of-range integers, fractional SHORTs and DECIMAL overflow are reported from the parser's JSON shape (with position/token) before Validate() runs. Validate() keeps the same checks as defence in depth. Other findings: BLOB writes work through F{PROP:Blob, -memoNbr} (negative index, matching the read path; the plan's positive index was wrong) and were verified end to end on MEMOS.TPS; text memos write through F{PROP:Value, -memoNbr}; DECIMAL display trims trailing fraction zeros (10.00 reads back as "10", consistent with pre-existing 0 → "0"); INSERT into a leaf inside a DIM'd GROUP is rejected UNSUPPORTED per the Task 7 ruling, untested because no corpus file has one.

Task 9 — UPDATE and DELETE, two-pass, transactional · 6928a19

Task 9 · Done · 6928a19

Rollback proven against a live hold

The hold case is the deliverable's proof: tests\hold.exe opens the work copy of KEYS shared and HOLDs row 2 for eight seconds; DELETE ... WHERE ID > 0 then deletes row 1 inside LOGOUT, hits error 43 (IsHeldErr, ERRORS.CLW:23) on row 2, and reports RECORD_HELD, row "2", matched 5, affected 0, outcome rolled_back, exit 3. A SELECT afterwards shows all five rows, so ROLLBACK undid an already-applied DELETE. LOGOUT(2,F) works on the file as tpsSchema opens it (SHARE), so no non-transactional downgrade was needed. The driver's error-40 text is bare "Creates Duplicate Key", which is why the key-name fallback exists.

Task 9 · Done · 6928a19

  • The plan's candidate queue type PosQ does not exist and the name crashes NEW (Task 7); SortQ is used.
  • The plan hardcodes exit 3 for a failed SET-literal Validate; UNSUPPORTED (leaf inside a DIM'd group) is exit 1, so the code uses DoInsert's rule.
  • The plan's Assign loop ignored failure; inside a transaction with a record held that would leak the hold, so an Assign failure now RELEASEs, rolls back and POPBINDs.

Task 10 — verify.ps1, README, release prep · 9df1585

Task 10 · Done · 9df1585

What the end-to-end verifier found

  • DESCRIBE does not expose the OVER marker or the picture, so verify.ps1 joins --dump-schema (which has neither ok nor complete) onto the DESCRIBE tree to build its round-trip rows.
  • An INDEX is populated only by BUILD, which nothing here issues, so --walk-key IDX reports count 0; the verifier accepts a zero count for an INDEX and still requires ordered. Consequence checked in review: ORDER BY must never select an INDEX.
  • A STRING declared with a picture deformats on assignment: 'rrr' stores 00000.00 with ok: true. Picture columns are left out of the round trip and the behaviour is documented; classification (warning vs VALUE_OUT_OF_RANGE) is a spec decision recorded in the final review.
  • Step 7 (SELECT ... LIMIT 1 median under 250 ms) is dominated by process start and fails when the machine is pinned by another process; the spec bound is kept and the measured baseline (30–60 ms idle) recorded.
  • tests\select.ps1 and tests\parser.expected.txt were LF only in the working tree but already CRLF in the index; normalising them produced no diff.

Task 10 · Done · 9df1585

Review fixes: two product defects the verifier exposed

  • ORDER BY could select an unbuilt INDEX. tpsExec.ChooseKey filtered only OPT keys; an INDEX is populated only by BUILD, which tpscli never issues, so a SELECT whose only matching key was an INDEX returned zero rows with ok: true. ChooseKey now skips IsKey = 0 and falls back to the in-memory sort. No corpus file reached the old path (KEYS.DUPKEY precedes KEYS.IDX), so there is no regression test; the trade-off is that a built INDEX is no longer used for ordering.
  • Picture STRING silently zeroed unreadable literals. INSERT ... PIC = 'rrr' reported ok: true and stored 00000.00. Spec §8 calls every conversion failure VALUE_OUT_OF_RANGE, so Validate now applies DEFORMAT(lit, '@' & picture) and rejects a literal that deformats to blank (or to zero while containing no digit) with "PIC does not match picture @N9.2". Probe results: 'rrr' → blank (rejected); '7' → 7; '00007.00' → 7; '' accepted; 'r7r' → 7 (accepted, known ceiling: FORMAT does not take a runtime picture, so a round-trip check is impossible). Seven cases added to tests\insert.ps1; verify.ps1 asserts the refusal on every picture column.
  • verify.ps1 now FAILs (not skips) a file whose unique key has an unwritable component, joins schema metadata by field ordinal from --dump-schema instead of bare labels, and survives a failing test script in step 2.
