1 · OverviewWhat we are building

One executable, tpscli.exe, that takes a SQL statement, opens the named TopSpeed file, and does what the statement says. It reads the table layout out of the file itself, so it works on any .TPS from any Clarion shop without a dictionary, a layout argument, or a rebuild when the file changes.

Writes go through the real TopSpeed driver via SoftVelocity's runtime file class (DynFile, shipped as full source in C:\Clarion12\libsrc\win\DynFile.inc and DynFile.clw), so every key is maintained exactly as the register maintains it. Nothing in this design writes TPS pages by hand.

Three reasons the surface is SQL: nobody learns a new interface, an LLM already speaks it, and a human can drive the exe from a shell without the MCP.

Non-goals

Row CRUD only. No CREATE TABLE, ALTER, DROP, pack, key rebuild, joins, aggregates, subqueries, or transactions spanning statements. No layout-as-argument. No long-lived server mode. Each of these can be added later without changing the SQL surface.

3 · SurfaceCommand line and SQL dialect

Invocation

tpscli.exe [--owner <string>] [--table] [--limit-default N] "<sql>"
tpscli.exe [options] < statement.sql
tpscli.exe --version
  • SQL comes from the first non-option argument, or from stdin when no argument is given.
  • --owner is the TopSpeed owner (encryption) string. It is never echoed in output or errors.
  • --table renders results as an aligned text grid instead of JSON. Everything else is identical.
  • --limit-default caps a SELECT that has no LIMIT. Default 1000. LIMIT 0 means no cap.
  • --parse-only runs syntax and schema validation for one statement (it opens the file to read the definition) and never touches a record. Success returns ok, op, parse_only: true and complete; failures use §8.
  • Exactly one statement per invocation. Unknown options, an option without its value, a second positional argument, empty SQL, or more than one statement are rejected with SYNTAX before anything is opened.
  • LIMIT, OFFSET and --limit-default must be non-negative integers up to 2,147,483,647.

Table names are file paths

The identifier after DESCRIBE, FROM, INTO, or UPDATE is a path to a .TPS file, written in square brackets: [C:\pos\data\ITEMS.TPS]. Brackets are always accepted and are required when the path contains spaces, backslashes, or a drive letter. A bare unbracketed name resolves relative to the current directory. Note the shell quotes around the whole statement are separate from this rule.

Statements

DESCRIBE <file>
SELECT <cols | *> FROM <file> [WHERE <expr>]
       [ORDER BY <col> [ASC|DESC], ...] [LIMIT n [OFFSET m]]
INSERT INTO <file> (<cols>) VALUES (<values>)
UPDATE <file> SET <col> = <value>, ... WHERE <expr>
DELETE FROM <file> WHERE <expr>

Expression grammar (WHERE)

SQLBecomes (Clarion filter)Notes
= <> != < > <= >== <> <> < > <= >=Direct.
AND OR NOT ( )SameStandard precedence: NOT, AND, OR.
'text''text'Doubled quote escapes. Case-sensitive, trailing spaces ignored (Clarion string compare).
123, -4.5Same
col LIKE 'AB%'MATCH(col,'AB*',1)% becomes *, _ becomes ?. The mode is the literal 1 (Match:Wild), since equates are not visible to runtime expressions.

col IS NULLRejectedTPS has no NULL. Compare to '' or 0 instead. The error says so.

Column names are resolved against the file's schema before anything runs. An unknown column is a parse-time error naming the column and listing the valid ones. Group members are addressed with dots, array elements with brackets, and each dimension is indexed at the component that owns it: ADDR.CITY, QTY[3], ADDR[2].CITY, GRID[2][3]. Subscripts are 1-based. In a SELECT list, naming a group or a whole array expands to its scalar leaves in declaration order, and * uses the same expansion. Assignments in INSERT and SET must address individual leaves. Missing, extra, or out-of-range subscripts are rejected before anything is opened for write.

What is rejected

Anything outside the grammar above is refused with a parse error that quotes the offending token and position. That includes JOIN, GROUP BY, HAVING, DISTINCT, aggregate functions, subqueries, UNION, arithmetic in expressions, UPDATE or DELETE without WHERE, INSERT with no column list, an INSERT whose column and value counts differ, and a column named twice in one INSERT list or SET clause.

Exit codes

CodeMeaning
0Statement ran. ok is true.
1Syntax or validation error. No data was modified. Schema validation may have opened and read the file.
2File error: not found, unsupported definition, wrong owner string, access denied.
3Runtime error during execution: lock conflict, duplicate key, driver error. Writes were rolled back when the rollback itself succeeded; see outcome in the contract below.

Error JSON goes to stdout so a caller reading one stream gets everything. Diagnostic noise, if any, goes to stderr. In JSON mode, complete is the last top-level member before the closing brace. In table mode the last line is a summary ((n rows) or ERROR CODE: message) and the exit codes are the same. A missing or unparseable final object means the response is incomplete and the write outcome is unknown; it proves neither commit nor rollback, and the caller must not assume affected: 0 or retry on its own.

Response contract

  • Every response has boolean ok and complete, and op (one of describe select insert update delete, or null when the statement could not be recognised).
  • DESCRIBE success: file, encrypted, records, columns, keys. Columns keep their nested members and dim metadata. Key attributes nocase and optional are omitted when false.
  • SELECT success: columns, rows, row_count, truncated. Every row array has the same length and order as columns.
  • INSERT success: affected. UPDATE and DELETE success: matched and affected.
  • With --parse-only the success object is only ok, op, parse_only: true and complete; the operation-specific members above are absent.
  • Failure: error.code and error.message, plus whichever of these apply: error.position and error.token (syntax), error.column, error.key, error.row (primary key value or position string), error.errorcode, error.fileerrorcode, error.fileerror (driver). Write failures also carry outcome: "none" (no data changed: validation failed before any write, or a single-row INSERT was rejected by the driver), "rolled_back" (a transaction was open and ROLLBACK returned no error), or "unknown" (ROLLBACK or COMMIT reported an error, so the state on disk is not known). WHERE_REQUIRED and other exit-1 errors carry "none".
  • Non-fatal truncation of a string value adds a warnings array of { "code": "STRING_TRUNCATED", "column": ..., "message": ... }.
  • The exe accepts SQL only. There is no JSON request format.

5 · InternalsFour units, one file each

UnitDoesDepends on
tpsSchemaReads the TPS header and table-definition record in binary; produces a schema queue (fields, groups, arrays, memos, keys). Populates a DynFile from it.Nothing but the runtime. StringTheory for byte access.
tpsSqlTokenizer and recursive-descent parser for the five statements. Produces a statement record: op, file, columns, values, WHERE as a Clarion filter string over bound names, ORDER, LIMIT, OFFSET (default 0). Validates every column against the schema.tpsSchema, StringTheory.
tpsExecRuns the statement against the DynFile FILE: VIEW with FILTER and ORDER for reads and row matching, HOLD/PUT/DELETE for writes, LOGOUT/COMMIT around multi-row statements.DynFile, ClaTPS driver.
tpsOutJSON writer and the --table grid. Type-driven value formatting (ISO dates, decimal strings).Nothing.

Schema mapping

The TPS definition record stores a type code, size, and decimal places per field, plus group nesting and array dimensions. The type codes are taken from the tps-parse reference implementation at build time and pinned in a table in tpsSchema. Record fields, groups and arrays go to DynFile.AddField (a TFieldGrp with Type, Size, Places, Dim, Fields). MEMO and BLOB go to DynFile.AddMemo (a TMemoGrp with Type M or B, Binary, size); they are not record fields and INSERT assigns them after CLEAR of the record. The flattened GROUP and DIM rules below describe SELECT columns and rows; DESCRIBE keeps the nested form shown in §4. The mapping is:

SREAL, REALSamenumbernumeric literal

DATEDATE"YYYY-MM-DD", blank date is ""'YYYY-MM-DD' or ''; an invalid calendar date is VALUE_OUT_OF_RANGE

Anything else—Open fails with UNSUPPORTED_FIELD_TYPE naming the field and the code. No partial layouts, no writes.

Key definitions map to DynFile.AddKey and AddFieldToKey: name, unique or duplicate, primary, case-insensitive, optional (exclude nulls), and per-component direction. TPS does distinguish DATE and TIME from LONG in the definition record, so ISO formatting is driven by real metadata, not guessed.

All assignment literals are converted and validated before the first mutation. The TopSpeed driver itself compares the declared structure against the file's stored definition at OPEN and fails with error 47 when they differ; that failure is surfaced as DEFINITION_MISMATCH (exit 2, no mutation). A file swapped for one with the same definition between the schema read and the open is indistinguishable and harmless: the statement runs against whichever file the driver opened. The open happens once per invocation and the same FILE reference is used for every subsequent operation.

DynFile lifecycle

Set driver, name, owner and encrypt flag; add every field, key, key component (with explicit field and key numbers and component rank) and memo; call FixFormat; then GetFileRef and open shared. FixFormat in the shipped class reports failure with a modal MESSAGE (DynFile.clw line 842), which would hang a console process. tpsSchema therefore declares tpsDynFile derived from DynFile and shadows FixFormat with a version that uses the protected rDynF reference and returns the error code silently. A construction failure ends the run with DEFINITION_UNREADABLE before anything is opened.

Binding and expressions

Runtime expressions cannot use dotted or subscripted names, so tpsSql maps every SQL field path to a synthetic bound identifier _Fn, where n is the leaf's ordinal in the flattened schema (ADDR.CITY might be _F7, QTY[3] _F11). User field names are never used as bound names, so no collision is possible. It calls BIND on each referenced leaf before execution, and UNBIND on the way out. The generated WHERE goes to the VIEW through PROP:Filter, ORDER BY through PROP:Order with a leading - on descending columns. An expression the runtime rejects is reported as SYNTAX with the generated text.

Execution detail

  • SELECT. Open a VIEW over the FILE with filter and order as above; the driver uses a key when the order matches one. Skip OFFSET matching rows, collect up to the effective LIMIT, then probe for one more match to set truncated. Rows are buffered and written after the scan ends. Projection is done in the writer.
  • INSERT. CLEAR the record, assign listed columns, assign memos, ADD. One row, no transaction.
  • UPDATE and DELETE. Two passes. Pass 1 walks the VIEW and, after each successful fetch, stores POSITION(file) of the underlying FILE as an opaque string. Only these candidates are eligible; rows that start matching later are not. Pass 2: LOGOUT(2, file) and check its error before touching anything. For each candidate: HOLD(file, 1), REGET(file, position), check the error immediately, re-evaluate the WHERE against the held record, RELEASE and skip if it no longer matches, otherwise PUT or DELETE (both release the hold). COMMIT at the end and check its error before reporting success. Any error in the loop or from COMMIT: preserve the original error, RELEASE if a record is still held (every exit from the loop body passes through this), ROLLBACK, check its result, and report outcome as rolled_back when ROLLBACK returned no error, else unknown. matched is the pass 1 candidate count. affected is the number of successful PUT or DELETE calls that were committed, including an UPDATE that wrote unchanged values. It is 0 when outcome is rolled_back, and omitted when outcome is unknown.
  • LIMIT and OFFSET on UPDATE and DELETE are rejected. Ties would make them nondeterministic.
  • Shared access. The file is opened with SHARE(). HOLD uses a one-second timeout (HOLD with no timeout waits forever). A held record fails the statement; there are no retries, because a retried write after a lost response could apply twice. The caller decides whether to rerun.

7 · VerificationRelease qualification checks

Writes are compiled in from day one; these checks do not disable them in an unqualified build. No release is tagged, and the README does not describe writes, until every item below passes. The checks exist because the single biggest risk is a reconstructed layout that differs from the stored one, which would let the real driver write correct keys against the wrong structure.

  1. Corpus. A testdata/ folder with: a copy of every TopSpeed file the dtpos dictionary defines (taken from a test store, not a live lane), plus hand-built files from a small Clarion generator covering every type in §5, groups, DIM, memos, blobs, and an encrypted file with a known owner.
  2. DESCRIBE parity. For each dtpos file, DESCRIBE output is diffed against a JSON export of the dictionary's definition for that table. Zero differences in name, type, size, places, dim, key composition and attributes.
  3. Round trip. For each corpus file: record a count and a TPSFix report, INSERT one row with every column set, SELECT it back and compare field for field, UPDATE every column, SELECT and compare, DELETE, then count and TPSFix again. Count unchanged, TPSFix clean, all keys still walk in order.
  4. Parser. A statement file with one line per grammar rule and one per rejection case, run one statement at a time through tpscli --parse-only, output diffed against expected. This is the one runnable check the parser leaves behind.
  5. Shared access. A second process holds the file open with the record held; tpscli reads succeed and the write reports RECORD_HELD with a clean rollback.
  6. Performance. Process start plus a keyed SELECT against the largest corpus file, timed. Target under 250 ms. If missed, a stdio loop mode is the upgrade path; the SQL surface does not change.

All six are scripted in one PowerShell file, verify.ps1, that exits non-zero on any failure. Success is read from the script's own comparisons, never from the exe's exit code alone.

9 · RisksKnown and accepted

RiskMitigation
Reconstructed layout differs from the stored one, producing wrong writes through a correct driver.Driver error 47 at OPEN catches structural mismatch (DEFINITION_MISMATCH). §7 checks catch the rest. Unknown types fail the open. No release until parity and round-trip pass on the full dtpos corpus.
The TPS definition format has corners the reference parsers do not cover.Fail closed. DEFINITION_UNREADABLE rather than a guess. Grow the corpus when a real file trips it.
Clarion string comparison semantics differ from SQL (case, trailing spaces).Documented in §3 as the dialect. Not hidden.
A write completes but the process is killed before the response.No automatic retries anywhere. A missing final JSON object tells the caller the outcome is unknown, not that nothing happened; the caller inspects the data before rerunning.
Application rules (defaults, relationships, business validation) are not enforced.Out of scope and stated in the README. This is a data tool, not a business layer.
Process-per-call is too slow for interactive use.Measured in §7. Upgrade path is a stdio loop; the contract does not change.
