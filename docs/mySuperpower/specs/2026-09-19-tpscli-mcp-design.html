1 · OverviewWhat we are building

mcp/ is a Model Context Protocol server, written in TypeScript on Node, that lets an LLM client (Claude Desktop, Claude Code, anything speaking MCP over stdio) run tpscli.exe on the machine that holds the TopSpeed files. It exposes the whole CLI surface: the five statements, --owner, --limit-default, --parse-only, --table and --version. It adds exactly three things the CLI does not have, all of them about running safely under an LLM: a read-only default, optional root folders with a file listing, and a process timeout that kills a hung exe.

The server never imports the Clarion sources. Its only knowledge of tpscli is the response contract and the exit codes in cli/README.md, and it passes that JSON through unchanged, so the README stays the single contract for both components.

Success looks like

  • A support person adds one line to a client config and the model can describe, select and (when enabled) change rows in any .TPS file on that box.
  • The model gets the same JSON a script would, including every error code, and is told plainly when a write's outcome is unknown.
  • npm test is green on a machine with no Clarion installed; the end-to-end suite runs when the exe and the fixtures are present.

2 · DecisionsWhat was chosen and why

QuestionDecisionWhy
LanguageTypeScript on Node 20+, official @modelcontextprotocol/sdk, zodNode is already on the box (the instrument recorder uses it); one built .js is the easiest thing to point a client config at.
Transportstdio, same machine as the filesNo listener, no auth story. The tool layer is transport-agnostic, so HTTP can be added later without touching the tools.
Tool shapeOne tool per statement with structured arguments, plus tps_query for raw SQLStructured tools give the model schemas it cannot get wrong; raw SQL keeps exact parity with the CLI for anything the structured form cannot express.
WritesRead-only unless started with --allow-writesThe person editing the config decides, not the model. Write tools are still registered so the model gets a clear WRITES_DISABLED instead of a missing tool.
Owner stringServer default (--owner / TPSCLI_OWNER) with a per-call owner overrideThe default keeps the secret out of transcripts; the override covers a second encrypted file without starting a second server.
File pathsAbsolute paths always; --root folders make bare names resolvable and enable tps_list_filesAd-hoc "look at this file" still works; a configured deployment gets discovery.
Result shapetpscli's JSON verbatim; format: "table" returns the --table grid as textOne contract to document and test. The grid reads better for wide results.
InternalsThree modules: runner, sql, serverThe builder and the runner are unit-testable without Clarion; a single file would tangle timeout handling with tool registration.

3 · SurfaceServer command line and the eight tools

Starting the server

node mcp\dist\server.js [--exe <path>] [--root <dir>]... [--allow-writes]
                        [--owner <string>] [--timeout <seconds>]
FlagDefaultMeaning
--exe <path>see discoveryPath to tpscli.exe.
--root <dir>noneRepeatable. Folders that bare file names resolve against and that tps_list_files lists. Each must exist at startup.
--allow-writesoffEnables INSERT, UPDATE and DELETE, structured and raw.
--owner <string>TPSCLI_OWNER env, else noneOwner string passed to every call that does not supply its own.
--timeout <seconds>60Wall-clock limit per exe invocation. Positive integer.

Exe discovery, first hit wins: --exe, then TPSCLI_EXE, then tpscli.exe in the directory that holds server.js, then ..\..\cli\tpscli.exe relative to that directory (the repository layout, where server.js is in mcp\dist). A missing exe, a missing root folder, or a bad flag value fails at startup with a message on stderr listing what was tried, not on the first tool call. Unknown flags are rejected the same way.

ToolArgumentsRuns

format is "json" (default) or "table". On tps_query, "table" with a statement that classify() reports as INSERT, UPDATE or DELETE is INVALID_ARGUMENT: the grid drops outcome, and a write's outcome is never dropped. where and order_by are raw fragments in the CLI's dialect (ORDER BY takes col [ASC|DESC], ...); the WHERE grammar is small enough that a JSON expression tree would add a second grammar without removing the first. Every tool description carries the three dialect facts the model needs without the README: paths go in square brackets, string literals use single quotes with '' for an embedded quote, and LIMIT 0 means no cap.

The file argument

A file that is absolute (drive letter or UNC) is used as given. Any other value is tried against each --root in order, and the first path that exists is used; with no roots, or no hit, the tool returns FILE_NOT_FOUND from the server before the exe runs, listing the folders tried. A resolved path that lies outside every root after normalisation (.. segments) is refused with FILE_NOT_FOUND too: roots are a convenience for bare names, not a second way to spell an absolute path. The resolved path is what goes inside the brackets. Absolute paths are not sandboxed; that is a deliberate non-goal (section 10).

4 · SQL builderThe part that is easy to get wrong

sql.ts is pure: string in, string out, no I/O. It owns every rule for turning arguments into a statement the CLI accepts.

InputRendered as
file path[C:\pos\data\ITEMS.TPS]; always bracketed. A ] in the path is rejected (INVALID_ARGUMENT) because the dialect has no escape for it.
column nameAs given, after checking it is a dotted path of identifiers, each with an optional integer subscript: ID, ADDR.CITY, QTY[3], ADDR[2].CITY (regex ^[A-Za-z_]\w*(\[\d+\])?(\.[A-Za-z_]\w*(\[\d+\])?)*$); anything else is INVALID_ARGUMENT. Subscript range, group expansion and write restrictions stay with the exe. Unknown names are left to the exe's UNKNOWN_COLUMN, which lists the valid ones.
JSON string'text' with every ' doubled.
JSON numberPlain decimal notation, exactly as JSON spells it without an exponent: 12.5, -4. A value whose JavaScript rendering contains e, a non-finite value, or an integer outside Number.isSafeInteger is INVALID_ARGUMENT (the dialect has no exponent form and the server will not round silently). Range and fraction errors for the column are the exe's VALUE_OUT_OF_RANGE.
JSON boolean1 / 0 (the dialect has no boolean literal; BYTE flags are numbers).
JSON nullINVALID_ARGUMENT: the dialect has no NULL (TopSpeed has no nulls). The message says to omit the column instead.
object / array valueINVALID_ARGUMENT. Dates, times and blobs are strings in the CLI's own formats (YYYY-MM-DD, HH:MM:SS.hh, base64); DECIMAL columns take a JSON number, because the exe requires a numeric literal for them (a quoted '12.50' is VALUE_OUT_OF_RANGE).
where, order_byVerbatim after trimming; empty string treated as absent. For tps_update and tps_delete an absent or empty where is INVALID_ARGUMENT before the exe would say WHERE_REQUIRED, so the message can point at the argument.
limit, offset, limit_defaultNon-negative integers up to 2,147,483,647 (zod), matching the CLI's range.
 
tps_select  { file:"ITEMS.TPS", columns:["SKU","DESC"], where:"PRICE > 5 AND DESC LIKE 'a%'",
              order_by:"SKU DESC", limit:20 }
  → SELECT SKU, DESC FROM [C:\pos\data\ITEMS.TPS] WHERE PRICE > 5 AND DESC LIKE 'a%'
      ORDER BY SKU DESC LIMIT 20

tps_insert  { file:"KEYS.TPS", values:{ ID:9, NAME:"O'Brien", CODE:"N" } }
  → INSERT INTO [C:\pos\data\KEYS.TPS] (ID, NAME, CODE) VALUES (9, 'O''Brien', 'N')

tps_update  { file:"KEYS.TPS", set:{ NAME:"niner" }, where:"ID = 9" }
  → UPDATE [C:\pos\data\KEYS.TPS] SET NAME = 'niner' WHERE ID = 9

classify(sql) returns the first word of a raw statement after leading whitespace, upper-cased, or null when there is none (the dialect has no comments, so nothing else is skipped). The policy layer uses it to decide whether a tps_query is a write; the exe remains the authority on whether the statement is valid.

5 · RunnerOne exe call, one result

runner.ts exports one function:

run(exe: string, args: string[], opts: { timeoutMs: number }): Promise<RunResult>

RunResult = { exitCode: number | null, stdout: string, stderr: string,
              json: object | null, durationMs: number, timedOut: boolean,
              failure?: { kind: "spawn" | "timeout" | "output_limit" | "kill_failed",
                          message: string, pid?: number } }
  • child_process.spawn(exe, args, { windowsHide: true, shell: false }). The SQL is one argv element; there is no shell and therefore no quoting layer. stdin is closed immediately so the exe never waits for it.
  • stdout and stderr are collected as UTF-8, up to a fixed ceiling of 64 MiB combined. Past the ceiling the process tree is killed and the result is INCOMPLETE ("output exceeded 64 MiB; add a LIMIT"), never a truncated success.
  • json is the parse of the whole trimmed stdout as one JSON object (the exe writes exactly one object; the parse does not assume it is one line). It counts as a response only when it is an object with complete === true and ok === (exitCode === 0); anything else, including {}, a partial object, or an ok that disagrees with the exit code, leaves json null and becomes INCOMPLETE. In table mode no parse is attempted and json is null.
  • On timeout the process tree is killed with taskkill /PID <pid> /T /F. A Clarion exe that crashes sits behind a modal dialog; a plain child.kill() leaves that dialog on screen and the handle open. The promise settles exactly once: on the child's close (after stdout and stderr have drained, which exit does not guarantee), on a spawn error, or when a kill attempt fails or passes its own 5 s deadline, in which case it settles without waiting for the child. The timer is cleared whichever way it settles.
  • Every runner-level failure is reported in failure, not inferred from stderr: a spawn failure (kind:"spawn", the system error as the message, exitCode null), a timeout ("timeout"), the output ceiling ("output_limit"), and a taskkill that fails or does not return within 5 s ("kill_failed", with pid, message saying the process may still be running). timedOut is set by the timeout itself and survives a later kill_failed, so the response's timed_out maps from it directly. The server builds the INCOMPLETE message from failure.message.
  • The owner string, when present in args, is never logged. The runner has no logging of its own; the server logs one line per call to stderr (tool name, duration, exit code) and nothing from argv.

From RunResult to a tool result

Evaluated in this order, first match wins: a failure, or an exitCode that is null or outside 0 to 3, is INCOMPLETE whatever stdout holds (a timeout that races a complete exit is still a timeout); then table mode, which never looks at json; then JSON mode, where a null json is INCOMPLETE.

CaseTool result
exit 0, json presentstructuredContent = the object; content = [{ type:"text", text: <the object pretty-printed> }]. isError false.
exit 1, 2 or 3, json presentSame shape as success; isError true. The exe's error.code and error.message are the explanation, and outcome is passed through for writes.
format: "table", exit 0 to 3content = [{ type:"text", text: stdout verbatim }]: the grid plus its summary line, or on failure the exe's single CODE: message line. isError = exit ≠ 0. No structuredContent. Table mode is read-only by construction (section 3), so no outcome is lost.
any failure, exit outside 0 to 3 or null; or, in JSON mode, no valid objectisError true with a server-made object { ok:false, complete:false, op, error:{ code:"INCOMPLETE", message }, exit_code, timed_out, stderr }, plus outcome:"unknown" when the statement was a write. The message repeats the README's rule: the response is incomplete, a write's outcome is unknown, do not retry without checking.

isError follows the exe: any non-zero exit is an error result, so a client that renders errors differently does the right thing, and the model still receives the full object. No tool declares an outputSchema: the SDK would then require structuredContent on every success, and table results have none.

6 · PolicyApplied before anything is spawned

RuleWhereEffect
Writes disabled (no --allow-writes)tps_insert, tps_update, tps_delete; tps_query when classify() returns INSERT, UPDATE or DELETEWRITES_DISABLED, message says which flag enables them. A tps_query with parse_only: true is allowed regardless: it never touches a record.
RootsStructured tools' fileSection 3, "The file argument". tps_query is exempt: its SQL is the model's, verbatim.
OwnerAll exe-running toolsPer-call owner if given, else the server default, else no --owner flag. Passed as its own argv element, never interpolated into the SQL.
TimeoutAll exe-running toolsServer-wide value; not overridable per call.

Server-made errors (WRITES_DISABLED, NO_ROOT, FILE_NOT_FOUND from resolution, INVALID_ARGUMENT, INCOMPLETE) use the exe's error shape, { ok:false, complete:true, op, error:{ code, message } }, so the model sees one error format. op is the statement's operation when the tool implies one (describe, select, insert, update, delete; for tps_query the lower-cased classify() result when it is one of those five) and null otherwise. A write refused before launch carries outcome:"none", as the exe's own pre-write refusals do. complete is true for all of them except INCOMPLETE: nothing ran, so nothing is unknown.

Argument-shape failures are the SDK's: registerTool validates the zod schema before the handler runs and answers a JSON-RPC InvalidParams error (Input validation error: Invalid arguments for tool ...), which the SDK client surfaces as a thrown McpError, not a tool result. The envelope above applies to everything the handler itself refuses (empty set, a bad column name, a null value, offset without limit).

7 · Data flowOne structured call, end to end

client   tools/call tps_update { file:"KEYS.TPS", set:{NAME:"niner"}, where:"ID = 9" }
server   zod (SDK): argument shapes valid
server   handler: set non-empty, where non-empty, column names well-formed
server   policy: --allow-writes present?  no  → WRITES_DISABLED, return (isError)
                                          yes → continue
server   resolve: KEYS.TPS against roots → C:\pos\data\KEYS.TPS (exists)
server   build:  UPDATE [C:\pos\data\KEYS.TPS] SET NAME = 'niner' WHERE ID = 9
server   argv:   [--owner, <default>]? + [<sql>]
runner   spawn tpscli.exe, 60 s limit, collect stdout
exe      { "ok": true, "op": "update", "matched": 1, "affected": 1, "complete": true }   exit 0
server   structuredContent = that object; content = pretty JSON; isError = false
server   stderr: tps_update 41ms exit 0
client   renders the result

9 · VerificationWhat green means

Unit (no Clarion needed)

  • sql.test.js: every row of the section 4 table has at least one passing and one rejecting case; the three examples in section 4 are asserted byte for byte; classify() on leading whitespace, lower case, and an empty string.
  • runner.test.js with the fake: exit 0 with JSON; exit 3 with JSON; ok:true with exit 1 (json null); complete:false (json null); table mode (json null, stdout intact); garbage stdout; empty stdout; a spawn of a path that does not exist; stdout past the ceiling (killed, INCOMPLETE); a hang that trips a 500 ms timeout and leaves no child process behind (checked with tasklist).
  • server.test.js with a stub run(): the tool list is exactly the eight tools; WRITES_DISABLED with outcome:"none"; parse_only passing the gate; NO_ROOT; bare name resolved against two roots in order; a .. escape refused; format:"table" on a raw write refused; the argv handed to run() for each tool, owner as its own element.

End to end (real exe, real fixtures)

  • One call per tool against the copied corpus: tps_version, tps_list_files (six files), tps_describe KEYS, tps_select with where/order/limit and again with format: "table", tps_insert / tps_update / tps_delete of one row under --allow-writes, tps_query raw select.
  • SECRET.TPS without owner → OWNER_REQUIRED passed through with isError; with owner: "s3cret" per call → ok; with TPSCLI_OWNER in the server's env → ok.
  • Read-only server: tps_delete → WRITES_DISABLED; tps_query with a DELETE and parse_only: true → ok with parse_only: true.
  • tps_update without where is rejected by the schema; tps_query "UPDATE ... SET X = 1" under --allow-writes → the exe's WHERE_REQUIRED.

Manual gate, recorded in the implementation notes

  • Register the server in Claude Code's MCP config on this machine with --root pointing at a temp folder holding copies of the six fixtures, call each of the eight tools once from a conversation (the writes and the raw query against those copies only), and paste the results into docs/mySuperpower/implementation-notes/ for the MCP.

10 · Risks and non-goalsKnown and accepted

RiskMitigation
The model writes a where that matches more rows than intended.Read-only default; the client's own tool-approval prompt; tps_select with the same where first is the documented habit in the tool description. The server does not add a dry-run of its own: --parse-only validates syntax, not row counts, and inventing a count-first step would double every write's I/O.
A hung or crashed exe holds a file open.Timeout with tree kill. The default of 60 s is generous for a single-statement scan; a full scan of a very large file can be raised with --timeout.
Owner string in transcripts.Server default is the documented path; the per-call override is described as "for a second encrypted file", and the value is never echoed by the exe or the server.
Two contracts drift (README vs. tools).There is one: the server passes the exe's JSON through. Server-made errors reuse its shape and are listed in mcp/README.md.
Absolute paths reach anything the user can read.Accepted. The server runs as the user, on the user's machine, for the user's files; sandboxing absolute paths would only move the fence to a flag the same person sets.

Non-goals

  • HTTP transport, authentication, multi-user.
  • MCP prompts or resources; the dialect summary lives in the tool descriptions.
  • Batches or transactions across statements (the exe is one statement per process).
  • Reshaping rows into objects, pagination helpers, or result caching.
  • Recursive root listing; POS data folders are flat.

11 · Self-reviewChecked before hand-off

  • No placeholders: every flag has a default, every tool has its argv mapping, every error has a code and a shape.
  • Consistency: format: "table" yields json: null in the runner, no structuredContent in section 5, and is refused for raw writes in section 3; parse_only bypasses the write gate in sections 3, 6 and 9; roots apply to structured tools only in sections 3 and 6; every server-made write refusal carries outcome:"none" and every INCOMPLETE write outcome:"unknown".
  • Checked against the exe on 2026-09-19: a quoted decimal is refused (VALUE_OUT_OF_RANGE), 1e-7 is not a literal, OFFSET without LIMIT is SYNTAX, table-mode failures print one CODE: message line. Section 4 follows those facts.
  • Scope: one implementation plan. The three modules and the three test files are the whole deliverable; the manual gate is one sitting.
  • Ambiguity resolved: bare-name resolution is first-existing-hit in root order; limit omitted vs. 0 mirrors the CLI and offset needs limit; boolean renders as 1/0; null is rejected rather than guessed; numbers are plain decimal or refused.
  • Reviewed by Codex (round 1, 13 findings; round 2, 6 findings; round 3, 2 findings): all accepted; three were checked against the running exe first.
