Spec · Design

Roots at runtime, reads that leave no mark

A tool that changes the server's roots while it runs, a file listing for any folder, and reads that leave the file's modified time alone.

2026-09-20

Source
Tickets docs/tickets/2026-09-19-tps-list-files-without-root.md and docs/tickets/2026-09-20-reads-open-read-write.md, plus the request to change the root without restarting the server. Brainstormed 2026-09-20.

1 · OverviewThree small changes, one plan

The MCP server (mcp/) takes its root folders once, from --root on the command line, and a server registered without any (the plain claude mcp add -s user tpscli -- node ...\dist\server.js --allow-writes) answers tps_list_files with NO_ROOT for the whole session. Changing the folder the model works in means re-registering the server and starting a new session. Separately, the CLI (cli/) opens every file with SHARE() (ReadWrite + DenyNone) whether the statement reads or writes, so a DESCRIBE or a SELECT moves the file's LastWriteTime without changing a byte.

This spec fixes all three. It is an addendum to the 2026-09-19 MCP design (docs/mySuperpower/specs/2026-09-19-tpscli-mcp-design.html) and supersedes, in that spec, the eight-tool inventory, the tps_version result, the tps_list_files contract, the startup-only meaning of roots and the NO_ROOT code. The earlier spec is history and is not edited; the active documents (READMEs, guides, tests, instruments) describe the replacement behaviour. Everything else in that spec stands.

tps_set_rootsninth tool

tps_list_files + directorylists any folder in one call

tpsSchema.Open(writing)DESCRIBE / SELECT open ReadOnly

Success looks like

  • In a running session the model is told "work in C:\...\CONFIG", calls tps_set_roots, and from then on lists that folder and opens files by bare name; no re-registration, no new session.
  • tps_list_files({ directory }) lists a folder on a server that has no roots at all.
  • A folder of production copies hashes and timestamps the same after a describe-and-select pass as before it, and a read works on a folder the account can only read.

3 · tps_set_rootsThe ninth tool

FieldValue
TitleSet root folders
Inputroots: string[], required. Empty array clears the set.
Result{ roots: string[] }, the set now in force, resolved and in order.
ExeNone. No file is opened.
GateNone. Allowed on a read-only server.
LogOne stderr line, tpscli-mcp tps_set_roots 2 root(s): C:\a; D:\b (or 0 root(s)), matching the per-run lines. Folder paths already appear in the ready line, so this logs nothing new in kind.

Validation runs over the whole array before anything changes, so a bad entry leaves the current set exactly as it was (all-or-nothing). Each entry must be fully qualified by the same test the file argument uses (FULLY_QUALIFIED: a drive letter followed by a separator, or a UNC path); a relative root would resolve against the server process's working directory, which the model cannot see. Each entry is then path.resolved and must exist and be a directory, the same check parseArgs applies to --root. Duplicates after resolution are dropped, compared case-insensitively because the file system is; the first occurrence keeps its place. The array then replaces the server's root state. That state is the server's own: createServer copies config.roots at construction and never writes back to the Config it was given (the unit tests build several servers from one shared base object, so a setter that wrote through would leak into other tests). resolveFile and tps_list_files read that state at the start of every call, so bare-name resolution follows the new set from the next call on.

Two existing strings speak of startup flags and become false once roots can change: the resolver's no-roots refusal (server.ts line 85, "the server was started without --root folders") becomes X is not an absolute path and the server currently has no root folders; call tps_set_roots or pass an absolute path, and FILE_ARG's description (line 71) says bare names resolve inside the server's current root folders. The assertion on that message in server.test.js (line 80, /--root/) follows.

The tool description, which is what the model reads, says: Replaces the server's root folders for this session: where bare file names resolve and what tps_list_files lists by default. Absolute paths; each must be an existing folder. Pass [] to clear. Roots are a convenience, not a fence: every tool accepts an absolute path regardless. A restart returns to the --root flags.

tps_version's successful result gains roots: string[] beside server and exe, snapshotted when the call starts, so the current set can be read without changing it. On failure the existing error result is returned without roots: the exe's error passthrough, or the server's INCOMPLETE envelope on a timeout or a bad exit; the resolver's own FILE_NOT_FOUND for a bare name still names the current roots or their absence (an exe-generated FILE_NOT_FOUND passes through unchanged, as today). The startup ready line is unchanged; it reports the flags the server was started with.

Validation and replacement run synchronously, without yielding, so no call can observe a half-built set. A call already in flight keeps the path it resolved before it awaited the exe. The SDK does not serialise handlers, so a client must await a successful tps_set_roots reply before issuing the calls that depend on it; requests in flight at the same time have no guaranteed order relative to the setter.

4 · tps_list_filesAny folder, one level deep

CallBehaviour
{}, roots setAs today: every root, one level deep, sorted by path.
{ directory }That folder only, one level deep. Allowed whether or not the server has roots and whether or not the folder is inside one. directory must be fully qualified and an existing folder, else INVALID_ARGUMENT naming the value.
{}, no rootsINVALID_ARGUMENT: The server has no root folders; pass directory, or call tps_set_roots first. Replaces NO_ROOT, which is removed from the server, the tests and the active documents; the 2026-09-19 spec stays as section 1 says.
patternUnchanged; applies in both modes.

The result shape does not change: { files: [{ name, path, size, modified }] }. The description becomes: Lists the .TPS files directly inside a folder (no recursion): name, path, size and modified time. With directory, that folder; without it, the server's root folders (see tps_set_roots).

Validation (existsSync, statSync) and enumeration (readdirSync, the per-entry statSync) can throw: access denied, a folder removed between the check and the read, an entry removed mid-listing. Today those exceptions escape attempt, which only envelopes InvalidArgument and ToolError; the SDK then returns a text-only tool error without the structured envelope, which the model cannot read by code. Both tools catch them and answer INVALID_ARGUMENT with the path and the OS message (cannot list C:\x: EPERM ...); a listing that fails part-way returns no partial result, and a root validation that fails leaves the set unchanged. Two unit tests: a directory that names a file exercises validation (isDirectory() false); a server constructed with a root that names a regular file (the tests build servers from a Config directly, bypassing parseArgs) makes readdirSync throw inside tps_list_files {} and must yield the structured INVALID_ARGUMENT envelope, which proves the catch is there.

INVALID_ARGUMENT rather than FILE_NOT_FOUND for a missing folder keeps one rule: FILE_NOT_FOUND is for a file the exe or the resolver could not find, INVALID_ARGUMENT is for an argument the server refused before looking. tps_set_roots uses the same code for the same reason.

5 · CLIReads open ReadOnly

tpsSchema.Open becomes Open PROCEDURE(BYTE writing),LONG in cli/tpsSchema.inc and cli/tpsSchema.clw. With writing = 0 it runs OPEN(SELF.F, 40h) (ReadOnly + DenyNone); with writing = 1 it runs SHARE(SELF.F) as today (ReadWrite + DenyNone, 42h). The CASE ERRORCODE() mapping that follows the open (47 to DEFINITION_MISMATCH, 2/3 to FILE_NOT_FOUND, else DRIVER) and the field-number mapping into Who are unchanged.

Call site in cli/tpscli.clwPasses
Line 189, the DESCRIBE branch (also serves --walk-key)0
Line 224, after ParseBody, for SELECT, INSERT, UPDATE, DELETECHOOSE(Stmt.Op = OP:Select, 0, 1)

--parse-only halts before the second call site (line 218 is after ParseBody), so SELECT, INSERT, UPDATE and DELETE with --parse-only never open the file; DESCRIBE --parse-only takes the first call site and does open it, ReadOnly after this change, so the ticket's expectation for --parse-only is met by the DESCRIBE branch and needs no code of its own. tpsSchema.Load reads the file's bytes through StringTheory's LoadFile, a plain read, and is not the cause of the timestamp move; it stays as it is. --dump-schema halts after Parse, before Open, and is unaffected.

Watch-point for the first CLI task

The TopSpeed driver's behaviour on a ReadOnly open of a structure the CLI reconstructed from the file is the one thing this spec has not observed. The plan's first step is the failing test below; if the driver refuses a ReadOnly open (error 47 or a driver error where SHARE succeeds), the implementer reports it with the exact codes and the fallback is chosen from evidence (for example ReadOnly + DenyWrite), not assumed here.

Documentation follows the behaviour: cli/README.md line 126 ("The file is opened with SHARE()") and the CLI user guide's tip at docs/UserGuide/Tpscli-IT-Support-User-Guide.html line 209 say that reads open ReadOnly and shared, writes ReadWrite and shared, and that a read leaves the modified time alone. RECORD_HELD wording is unchanged: it belongs to writes.

8 · TestingWhat green means

CLI (cli/tests/readonly.ps1, new; added to the suite list in cli/verify.ps1 step 2)

  • Copy testdata\KEYS.TPS to testdata\work\; record LastWriteTime; run DESCRIBE then a full SELECT; assert the time is unchanged and the SHA-256 is unchanged. Then run one UPDATE and assert the time moved, so the check is known to detect a regression.
  • Copy KEYS.TPS into testdata\work\ro\ and put a deny-write ACE on the file itself (icacls <file> /deny "<user>:(W)", where the user is $env:USERDOMAIN\$env:USERNAME). Control first: run one UPDATE and assert it fails (non-zero exit, DRIVER), which proves the ACE reaches the file; then run SELECT and assert exit 0 with rows. Remove the ACE in finally (/remove:d) and treat a failed removal as a test failure. An icacls that cannot apply the ACE is a failure too, not a skip: verify.ps1 step 2 knows only the suite's exit code, so a suite that prints SKIP and exits 0 would read as PASS.
  • The existing suites (describe, parser, select, insert, update) and verify.ps1 stay green; step 6's shared-access check (Step6-SharedAccess) still reports the read succeeding and the write as RECORD_HELD.

Server unit (mcp/test/server.test.js, no Clarion needed)

  • tps_set_roots with two folders: result lists both resolved, in order; a bare name then resolves inside the second; tps_list_files {} lists both.
  • A relative entry, and a missing folder, each return INVALID_ARGUMENT and leave tps_version.roots as it was.
  • Duplicates differing only in case collapse to one.
  • [] clears; a bare name is then FILE_NOT_FOUND; tps_list_files {} is INVALID_ARGUMENT.
  • tps_list_files { directory } on a root-less server lists the folder; with roots set and a folder outside them it still lists; with pattern it filters; relative or missing directory is INVALID_ARGUMENT.
  • Existing assertions that necessarily change: the tool inventory (line 47, now exactly nine names with tps_set_roots), the exact tps_version result (line 221, gains roots), the no-roots message match (line 80), and the NO_ROOT case (line 198 onward), which is replaced rather than kept beside the new one.
  • Two servers built from the same base config: setting roots on one leaves the other's unchanged.

End to end and the instruments

  • mcp/test/e2e.test.js: one case that sets the roots to the fixture folder, describes a bare name, and confirms the fixture's LastWriteTime did not move (this exercises the rebuilt exe through the server).
  • docs/Testing/TpscliMcp-Unit-Test-Cases.html: the NO_ROOT case becomes the directory and tps_set_roots cases; mcp/tests/run-instrument.ps1 follows and the run is re-recorded. This is the one place an existing runner file changes, because the behaviour it asserts is gone.
  • docs/Testing/TpscliMcpConfig-Unit-Test-Cases.html: TC-03 (currently the NO_ROOT case) becomes tps_set_roots to the CONFIG folder followed by a bare-name describe; TC-09's wording gains "and LastWriteTime unchanged". Re-run from a Claude Code session as before.

10 · Risks and non-goalsKnown and accepted

  • ReadOnly open refused by the driver. Covered by the watch-point in section 5: the first CLI test decides, and the fallback is picked from the observed error, not here.
  • A deny-write ACL test on a developer machine. icacls deny entries apply to administrators too, so the test is meaningful, and the UPDATE control proves the ACE took before the SELECT is credited. The finally removal keeps a failed run from leaving testdata\work\ro locked; a machine whose policy blocks icacls fails the suite, visibly.
  • The model sets a root and forgets. Roots are session state; a successful tps_version reports them and the resolver's FILE_NOT_FOUND for a bare name lists the folders searched, so the state is one call away whenever the exe answers.
  • Roots as a fence. They are not, before or after this change; the guide's caution stays as written. Anyone who needs a fence uses the account's permissions, which a ReadOnly open now respects for reads.

Non-goals

  • Persisting roots across restarts, or writing to the client's registration.
  • Add/remove semantics, recursive listing, or a --lock-roots flag.
  • Changing --allow-writes, --owner, --exe or --timeout at runtime. Only roots were asked for, and only roots are safe to change without a policy decision by the person who registered the server.
  • Any change to the CLI's JSON contract or exit codes.
